```markdown
# 04 — Crushing & splitting

**Role:** Prep technician
**Record:** [Crush / split worksheet](../forms/04-crush-split-worksheet.md)
**Outcome:** A defined coarse split proceeds; a retrievable reject is retained.

> **Batch handling:** A crusher/split run groups the work, while every member
> produces its own work-split and reject children, mass balance, and archive
> location.

## User flow

1. **Check readiness.** Scan the dried sample, inspect it, and record the
   crusher and riffle splitter IDs.
2. **Crush.** Run the jaw crusher under the configured method; record run
   identifiers and any cleaning or carryover controls.
3. **Split.** Riffle-split the crushed material into the working split and
   the reject; assign unique child IDs and weigh each portion where
   required.
4. **Archive the reject.** Bag, label, and shelf the reject, recording its
   archive/retrieval location.
5. **Sign off.** Send the working split to the pulverising queue; sign off
>  the worksheet and resolve any material-balance flag.

## Form fields entered

| Group             | Fields                                                                      |
| ----------------- | --------------------------------------------------------------------------- |
| Lineage           | Parent dried sample ID                                                      |
| Equipment & run   | Crusher ID/run, splitter ID, cleaning status                                |
| Child splits      | Work split ID and mass, reject ID and mass                                  |
| Balance & archive | Recovery or mass-balance result, reject bag/seal, shelf location            |
| Sign-off          | Operator, timestamp, deviations                                             |

## Controls and hand-off

- **Children, not replacements.** The working split and the reject are
  children of the same dried sample — new IDs pointing back to it, never
  substitutes for it.
- **The reject must be locatable.** A missing reject location blocks
  completion, and a material-loss exception must be explained.
```

A few things worth noting about how this stage changes the game:

- **The lineage stops being a chain and becomes a tree.** Up to here each stage handed one identity to the next: field ID → lab barcode (02) → dried ID (03). Doc 04 is the first fork — one parent spawns **two** children, one of which proceeds to pulverising and one of which parks in the archive. That's why the control insists on "children, not replacement IDs": the work split and reject are siblings sharing a parent, and both need to be traceable back through it.
- **The batch-handling rule is the DSP pattern again, one level down.** The run groups the work, but each member keeps its own children, masses, and archive location — a shared crusher run never merges identities, exactly as a shared dispatch never merged bags.
- **The reject is the audit anchor.** Every re-assay, duplicate, or check program pulls archived material rather than new field sampling — which is why the shelf location is a *blocking* field and mass loss needs an explanation. The reject's retrievability is the whole point of retaining it.
- **Mass balance is the first quantitative gate.** Docs 01–02 checked identity and condition; this is the first stage where numbers have to reconcile.

## 1. Product overview

The Product is an augmented-reality digital twin of a mine. It builds a 3D model of the site, keeps it updated with live data, and lets several people view the same model at the same time. People can join from an AR headset, a tablet, a phone or a web browser, on site or remote.

A local **edge node** at the mine keeps sessions running where connectivity is poor and syncs to the cloud afterwards.

### What it is for

- Giving planners, operations, safety and maintenance staff one shared visual picture of the site.
- Cutting travel and explanation time by letting remote people see what site people see.
- Showing live and historical site state in context.

### What it is not for

It is a shared visual and collaboration layer and decision-support viewer. It is **not** a replacement for mine planning suites, fleet management systems or SCADA, **not** a certified safety system, and **not** a source of legal, engineering or regulatory advice. See Section 14.

## 2. Core concepts

| Concept                             | Description                                                                                                                                     |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Site**                      | One mine, such as an open pit or an underground operation, with its own model, data connections and edge node.                                  |
| **Site model (digital twin)** | The 3D representation of the site. Built from client survey, CAD and GIS files and refreshed by drone or LiDAR**[Proposed]**.             |
| **Layer**                     | A set of information drawn on the model, such as live equipment positions, plan outlines or monitoring data. Layers can be switched on and off. |
| **Data source**               | An external system or file feed that supplies a layer, such as a fleet management export or a survey file.                                      |
| **Session**                   | A shared viewing room. Everyone in a session sees the same model state and can see each other's presence.                                       |
| **Participant**               | A person in a session, on a headset, tablet, phone or web.                                                                                      |
| **Annotation**                | A note, marker or drawing placed on the model and visible to session participants**[Proposed]**.                                          |
| **Edge node**                 | The on-site server that hosts sessions locally and syncs with the cloud.                                                                        |
| **Timestamp and freshness**   | Every live layer shows when its data was last updated, so users can judge how current it is**[Proposed]**.                                |

## 4. Feature reference

### 4.1 Core features

#### F1. AR digital twin **[Stated]**

Shows a 3D model of the mine that users can view in augmented reality or on a screen.

- **Headset or phone/tablet AR:** the model can be viewed overlaid on the real site, aligned to the physical position **[Proposed]**.
- **Tabletop or screen view:** the model can be viewed without alignment, from an office or at home.
- **Alignment accuracy:** pilot target of 0.5 m or better for overview tasks **[Target]**. Do not use the Product for tasks that need tighter accuracy until tested.
- **Open questions:** model update process, accuracy limits and supported file formats.

#### F2. Real-time data streaming **[Stated]**

Updates the twin with live data so the model reflects current conditions.

- Pilot sites connect one or two data sources **[Target]**.
- Display delay of 10 seconds or less from event to screen **[Target]**.
- Each live layer shows its last-updated time **[Proposed]**.
- **Open questions:** supported sources, protocols, data volume and failure behaviour.

#### F3. Real-time multi-user collaboration **[Stated]**

Several people view and discuss the same model in one session.

- Up to 12 concurrent users, on-site and remote mixed **[Target]**.
- Participants see who else is in the session **[Proposed]**.
- Annotations, pointers and shared view positions **[Proposed]**.
- Voice or chat is not described in the brief. Confirm whether the Product provides it or relies on an external call.

#### F4. Multi-device access **[Stated]**

The same session works across AR headsets, tablets, phones and web browsers.

- Feature parity between devices is unknown. Expect the headset to offer the richest AR view and the web the broadest reach **[Proposed]**.
- A device and model support matrix must be defined (Section 5).

#### F5. Hybrid deployment with edge sync **[Stated]**

Sessions keep running when site connectivity is poor.

- Local operation for at least one 8-hour shift offline **[Target]**.
- Changes made offline sync to the cloud when the connection returns.
- **Open questions:** conflict handling when the same item is edited in two places, edge hardware specification and power backup.

### 4.2 Candidate features (all [Unverified])

Do not describe these to customers as available until confirmed.

| Feature                                  | Intended function                                         | Key caution                                                                                    |
| ---------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Geofence and proximity alerts            | Warn when a person or vehicle enters or approaches a zone | Needs positioning hardware and safety validation. Never position as a certified safety system. |
| Slope and ground monitoring overlay      | Show movement readings against thresholds                 | Not a substitute for geotechnical engineers. No stability prediction.                          |
| Ore model, grade overlay, plan vs actual | Show the block model and compare plan with actual         | Depends on import fidelity.                                                                    |
| Drone and LiDAR updates                  | Refresh surfaces from new scans                           | Processing time unknown.                                                                       |
| 4D playback and what-if                  | Replay past site state and test options                   | Storage and fidelity unknown.                                                                  |
| Fleet and SCADA integration              | Show equipment status and positions                       | Needs vendor access and agreements.                                                            |
| Work-order overlay                       | Show maintenance work orders on equipment                 | Depends on the maintenance system.                                                             |
| Remote expert assist                     | An off-site expert views and annotates the equipment      | Bandwidth sensitive.                                                                           |
| AR training and emergency simulation     | Practise inductions and drills                            | Content creation effort.                                                                       |
| Compliance records and audit trail       | Record permits, inspections and access logs               | Regulatory acceptance unknown.                                                                 |
| CAD, GIS and planning-tool import        | Bring in existing site models                             | Format coverage unknown.                                                                       |
| Roles and data-residency options         | Control access and data location                          | Architecture unknown.                                                                          |

## 6. Getting started

All steps in this section are **[Proposed]** and describe the intended experience.

### 6.1 For a new site (administrator or onboarding team)

1. **Agree the pilot scope:** one site, one use case, one or two data sources, up to 15 users, one edge node.
2. **Collect inputs:** survey files, CAD or GIS models, access to one or two data feeds.
3. **Install the edge node** on site (Section 11) with network and power backup.
4. **Build the first site model** (Section 7).
5. **Connect data sources** (Section 8).
6. **Create user accounts and roles** (Section 12).
7. **Run a test session** with two or three people before the first real use.
8. **Record baselines** before launch (Section 16).

### 6.2 For a new user

1. Receive an invitation from your administrator.
2. Sign in on your device (headset, tablet, phone or web).
3. Open your site and review the model on screen.
4. Join a scheduled session, or start one.
5. In the field, align the model to the site if you are using AR (Section 9.3).

## 7. Building and updating the site model

### 7.1 Inputs **[Proposed]**

| Input                         | Examples                           | Status     |
| ----------------------------- | ---------------------------------- | ---------- |
| Terrain and surface survey    | Survey files, drone or LiDAR scans | Unverified |
| Design and engineering models | CAD files                          | Unverified |
| Spatial reference data        | GIS layers                         | Unverified |
| Plans                         | Mine plan outlines and schedules   | Unverified |

Supported file formats must be listed once confirmed.

### 7.2 Model build steps **[Proposed]**

1. Upload input files for the site.
2. Choose the coordinate system and confirm it matches the survey.
3. Run the build and review the result on screen.
4. Check against known landmarks. Record the measured alignment error.
5. Publish the model so sessions can use it.

### 7.3 Keeping the model current

The model is only as good as its last update. Define an update schedule per site, for example weekly after survey, or after each major change **[Proposed]**.

- Each model shows its **last updated date**.
- When a new scan or survey is processed, publish a new version rather than overwriting the old one, so past states can be compared **[Proposed]**.
- Users should treat an out-of-date model as unreliable for decisions.

## 8. Connecting live data

### 8.1 Principles

- Start with **one or two sources** the site already exports. Promise no source until it has been tested.
- Every live layer shows its timestamp and a freshness indicator.
- If a source stops updating, the layer should show that clearly rather than display stale values as current **[Proposed]**.

### 8.2 Connection steps **[Proposed]**

1. Identify the source and its owner (for example the fleet management system vendor).
2. Confirm access, format and update frequency.
3. Configure the connection on the edge node.
4. Map the incoming fields to a layer on the model.
5. Check a sample of values against the source system.
6. Measure the delay from event to display and record it.
7. Switch the layer on for users.

### 8.3 Source status

| Source type            | Status     | Notes                                       |
| ---------------------- | ---------- | ------------------------------------------- |
| Fleet management       | Unverified | Vendor access needed                        |
| SCADA                  | Unverified | OT security approval needed                 |
| Monitoring and sensors | Unverified | Thresholds belong to the client's engineers |
| Maintenance system     | Unverified | Needed for work-order overlay               |
| File-based exports     | Unverified | Likely the first pilot option               |

## 9. Running a shared session

All steps are **[Proposed]**.

### 9.1 Start a session

1. Open the site and choose **New session** (or open a scheduled one).
2. Choose which layers to show.
3. Invite participants by name or share a link.
4. Wait for participants to join. A presence list shows who is in.

### 9.2 During a session

- **Navigate:** move around the model or follow the presenter's view.
- **Point and annotate:** place markers and notes visible to everyone.
- **Switch layers:** turn live data, plans or monitoring layers on and off.
- **Check freshness:** look at layer timestamps before relying on live values.
- **Record outcomes:** capture decisions and actions before closing the session.

### 9.3 Aligning AR on site

1. Stand at a known reference point.
2. Open the AR view and select the matching reference.
3. Check alignment against two or more visible landmarks.
4. If the offset is above the accepted tolerance (pilot target 0.5 m **[Target]**), re-align or fall back to screen view.

### 9.4 End a session

1. Review the action list.
2. Save annotations and notes to the session record.
3. Close the session. Participants leave.

### 9.5 Session record

Each session should keep a record of participants, time, layers shown and annotations **[Proposed]**. Retention follows the client's data policy (Section 13).

## 10. Roles and workflows

These workflows come from the personas in the strategy document. Benefits are targets to measure in pilots, not promises.

### 10.1 Mine planning engineer: weekly planning review

**Goal:** align the plan with what actually happened and show it clearly.

1. Before the meeting, load the current site model and the plan layer.
2. Open a session and invite operations, geotechnical, HSE and maintenance staff.
3. Switch on plan and live or recent actual layers, and compare **[plan vs actual is Unverified]**.
4. Discuss variances in the shared 3D view and annotate decisions.
5. Record the revised sequence and action list.
6. After the meeting, share the session record.

**Do not claim:** that the Product replaces the planning suite or improves recovery or grade.
**Pilot metrics:** review duration, preparation hours, actions closed on time.

### 10.2 HSE manager: hazard briefing and induction

**Goal:** reduce exposure and evidence compliance.

1. Open the area after an incident, audit or new work area.
2. Mark hazards and exclusion zones on the model.
3. Brief crews in a shared session, in AR on site or on screen.
4. Record who attended and what was covered.

**Do not claim:** that the Product prevents incidents, is a certified safety system or satisfies regulatory inspection.
**Pilot metrics:** induction hours, briefing completion, clarity score. Alert latency only if alerts are built.

### 10.3 Maintenance planner and OEM service engineer: remote assist **[Unverified]**

**Goal:** shorten downtime and avoid expert callouts.

1. A technician on site opens a session at the equipment.
2. The remote expert joins by web, tablet or headset.
3. The expert sees the equipment in its site context and annotates what to check.
4. Record the repair and decide whether to escalate.
5. Log whether the callout was avoided.

**Do not claim:** fault-diagnosis accuracy, predictive maintenance, or integration with any named maintenance or fleet system until verified.
**Pilot metrics:** callouts avoided, time to repair, expert wait time.

### 10.4 Geotechnical engineer: movement review **[Unverified]**

**Goal:** turn monitoring data into access decisions that operations will act on.

1. On a movement alert or scheduled review, open the monitoring layer.
2. Show operations the affected area in 3D.
3. Issue an advisory or exclusion recommendation through the client's normal process.

**Do not claim:** early warning, stability prediction or replacement of engineering judgement.
**Pilot metric:** time from alert to operations briefing.

### 10.5 Underground operations: access and ventilation coordination

**Goal:** coordinate complex 3D access, ventilation and rescue planning.

1. Load the underground model on the edge node.
2. Hold the coordination session on the local network, with or without connectivity.
3. Review access routes and changes with the team.
4. Sync to the cloud when the connection returns.

**Do not claim:** gas or ventilation monitoring, or rescue-grade capability.
**Pilot test:** a stable session for 8 hours offline and clean sync after **[Target]**.

### 10.6 Mine manager or GM

Uses the session as an overview and decision forum. **Do not claim** production uplift. Metrics: review attendance and decision latency.

### 10.7 IT and OT security

Acts as gatekeeper. Needs the security whitepaper, data-flow diagrams and audit evidence. **Do not state** that the Product is "secure" without audit evidence. Metric: security review passed.

## 11. Edge node and offline operation

### 11.1 Purpose

The edge node hosts sessions locally so work continues when site connectivity is poor or lost, then syncs changes to the cloud.

### 11.2 Requirements **[Proposed, to be specified by engineering]**

| Item     | Requirement                                                                              |
| -------- | ---------------------------------------------------------------------------------------- |
| Hardware | To be defined (indicative one-off cost USD 8,000 to 15,000 if client-bought, assumption) |
| Power    | Backup power required, because site power is unreliable                                  |
| Network  | Local network reachable by on-site devices                                               |
| Storage  | Enough for the model, history and offline changes                                        |
| Location | A secure, ventilated place on site                                                       |

### 11.3 Offline behaviour

| Situation           | Expected behaviour**[Target]**           |
| ------------------- | ---------------------------------------------- |
| Connection lost     | On-site sessions continue on the local network |
| Remote participants | Cannot join until the connection returns       |
| Edits made offline  | Stored locally, then synced                    |
| Connection restored | Automatic sync, with a visible status          |
| Edit conflicts      | Rules to be defined before pilot               |

### 11.4 Sync status

The Product should show one of these states at all times **[Proposed]**: **Online and synced**, **Syncing**, **Offline (local only)**, **Sync error**. Users should never have to guess.

### 11.5 What to test in a pilot

- Session stays usable for at least 8 hours offline.
- Sync succeeds cleanly afterwards, with no lost annotations.
- Recovery after power loss on the edge node.

## 13. Security, privacy and data residency

Specific security claims require a security whitepaper and audit evidence. The points below are design intentions to confirm.

- **Data location:** hybrid deployment lets data stay on the edge node with cloud sync by policy **[Proposed]**.
- **Access control:** role-based access **[Unverified]**.
- **Audit trail:** records of who accessed what **[Unverified]**.
- **Personal data:** worker identity and position data may fall under Ghana's Data Protection Act, 2012 (Act 843). **Legal verification required.**
- **Data ownership:** the client owns its mine data. Contractors may need client permission to share data.
- **Third-party systems:** access to fleet, SCADA and monitoring systems requires the vendor's and client's approval.
- **Data retention:** to be agreed per client.

Do not describe the Product as secure, compliant or certified until evidence exists.

## 14. Limits and what the Product is not

| The Product is                                              | The Product is not                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------ |
| A shared visual and collaboration layer                     | A replacement for planning suites, fleet management or SCADA |
| A decision-support viewer of live and historical site state | A certified safety system                                    |
| A way to reduce travel and explanation                      | A source of legal, engineering or regulatory advice          |

### Operating cautions

1. **Alerts are decision support only.** If alerts are built, they must show latency and confidence and must supplement, never replace, certified safety systems.
2. **Check freshness.** Never act on a live value without checking its timestamp.
3. **Check alignment.** AR overlays are only as accurate as the alignment. Re-align if in doubt.
4. **Engineers keep responsibility.** Geotechnical, ventilation and safety decisions remain with qualified people.
5. **No unproven claims.** Do not quote savings, risk reduction or accuracy figures until pilots produce measurements.

## 15. Troubleshooting

All entries are **[Proposed]** and should be validated during pilots.

| Symptom                                | Likely cause                            | What to try                                                           |
| -------------------------------------- | --------------------------------------- | --------------------------------------------------------------------- |
| Model appears in the wrong place in AR | Misaligned reference point              | Re-align at a known reference and check two landmarks                 |
| Live layer shows old values            | Source stopped or sync delay            | Check the layer timestamp, the source system and the edge node status |
| Layer is blank                         | Source disconnected or mapping error    | Check the data source status and field mapping                        |
| Cannot join a session remotely         | Site connection down                    | Check the sync status. On-site users can continue locally             |
| Annotations missing after reconnecting | Sync error or conflict                  | Check the sync log and contact the administrator                      |
| Headset display is hard to read        | Glare, dust or heat                     | Switch to tablet or phone, or use shade and cleaning                  |
| Slow or choppy view                    | Weak network or heavy layers            | Switch off unused layers, move closer to the local network            |
| Cannot sign in                         | Account or role issue                   | Contact the site administrator                                        |
| Session limit reached                  | More than the supported number of users | Close inactive participants (target limit 12)                         |

### What to report to support

Site, device and model, time, session ID, layers on, sync status, and a screenshot **[Proposed]**.

## 16. Pilot measurement and KPIs

Value must be measured, not assumed. Record a 2 to 4 week baseline before launch.

| KPI                | Definition                                                  | Source                   |
| ------------------ | ----------------------------------------------------------- | ------------------------ |
| Review duration    | Start to end of a scheduled review                          | Calendar and session log |
| Preparation hours  | Hours spent preparing review materials                      | Time survey              |
| Callouts avoided   | Planned callouts resolved remotely                          | Service log              |
| Time to repair     | Fault reported to resolved                                  | Maintenance system       |
| Induction hours    | Hours per new worker                                        | Training records         |
| Active users       | Users with at least one session per week                    | Platform logs            |
| Non-headset share  | Non-headset sessions divided by all sessions                | Platform logs            |
| Data latency       | Event-to-display delay                                      | Platform logs            |
| Offline resilience | Hours a session stays usable offline, and sync success rate | Edge logs                |
| User clarity score | 1 to 5 survey rating                                        | Survey                   |

### Pilot template

- **Commercial:** paid pilot (base USD 15,000, assumption) credited against the first-year licence on conversion.
- **Scope:** one site, one use case, one or two data sources, up to 15 users, one edge node.
- **Duration:** 8 to 12 weeks.
- **Exit criteria:** agreed thresholds met, usage sustained, security approved.

Report hard savings (cash), soft savings (redeployed time) and contingent avoidance separately. Never add them together.

## 18. Glossary

**4D:** a 3D model that also shows change over time. **AR:** augmented reality. **ASM:** artisanal and small-scale mining. **CMMS:** computerised maintenance management system. **Concession:** a licensed mining area. **Digital twin:** a live digital model of a physical asset. **Edge node:** a local server at the mine that keeps the system running and syncs to the cloud. **FMS:** fleet management system. **Galamsey:** Ghanaian term for illegal small-scale mining. **GIS:** geographic information system. **LiDAR:** laser-based 3D scanning. **OEM:** original equipment manufacturer. **OT:** operational technology. **SCADA:** supervisory control and data acquisition. **Session:** a shared viewing room where participants see the same model.
